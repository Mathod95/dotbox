L'API●le service de Dot Box, par lequel passent la CLI et l'interface web.

The API●Dot Box's service, which the CLI and the web interface both go through.

Ce que c'est

Le binaire dotbox sert deux fois. Lancé en service, dotbox serve, il fait le travail: il pilote Docker, écrit les fichiers dans /opt et vérifie le serveur. Lancé en commande, dotbox status, il demande ce travail au service et affiche la réponse. L'interface web fait la même chose, par les mêmes routes.

  • Le service tourne en root, sous systemd (dotbox.service), installé et démarré par dotbox init avec le core.
  • Un seul binaire pour les deux: la CLI et le service ont toujours la même version.
  • Toute la logique est dans le service. La CLI n'a besoin d'aucun droit particulier, donc pas de sudo.

Deux portes, aucune sur Internet

PorteQui l'utiliseQui a le droit
/run/dotbox/dotbox.sock, un socket UnixLa CLI, sur le serveurRoot, et les membres du groupe dotbox. Le service vérifie qui appelle par le noyau, sans mot de passe ni jeton.
https://dotbox.example.com, par TraefikL'interface webUn compte Authelia du groupe admins, en two_factor.

dotbox init met ton utilisateur dans le groupe dotbox. Ce n'est pas le groupe docker: il ne donne que les actions de Dot Box, sur les apps du catalogue. Lancer un container quelconque, monter un dossier du serveur ou lire un secret reste réservé à root.

Ce qui le protège

  • Le service n'écoute jamais sur une adresse publique. Côté web, il écoute sur l'adresse du serveur dans le réseau dotbox, que seul Traefik doit joindre.
  • Traefik ajoute à chaque requête un en-tête secret, tiré par dotbox init et gardé dans /opt/dotbox/secrets/. Le service refuse toute requête web sans lui: une app du réseau dotbox ne peut donc pas l'appeler en se faisant passer pour Traefik.
  • Le service ne croit le nom envoyé par Authelia (Remote-User, Remote-Groups) qu'avec cet en-tête.
  • Les actions que seul root peut faire passent par sudo, sans le service: dotbox init, dotbox upgrade, dotbox restore, dotbox authelia, dotbox exec, dotbox edit, dotbox add et --local. Ce sont celles qui donneraient root à qui les lance: une commande dans un container, un compose ou une archive qui peuvent monter n'importe quel dossier du serveur.

Les routes

Du JSON en HTTP, sous /api/v1. Un changement qui casse les clients passera par /api/v2.

RouteCe qu'elle faitCommande
GET /api/v1/versionLa version du service et l'empreinte de son binaire: dotbox init le redémarre quand le binaire a changé
GET /api/v1/statusLe core et les apps: version, état, adresse, accès, le résumé du dernier doctor, et la dernière sauvegarde complète avec la prochaine (backup)dotbox status
GET /api/v1/doctorLe résultat du dernier doctor
POST /api/v1/doctorLance les vérifications et rend leur résultatdotbox doctor
POST /api/v1/appsInstalle des apps, {"apps": ["radarr", "sonarr"]}. Rend une tâche, qui se suit en directdotbox install
DELETE /api/v1/apps/{app}Retire une app (?purge=true pour tout effacer). Rend une tâchedotbox remove
GET /api/v1/jobs/{id}/eventsLes étapes d'une tâche en direct (Server-Sent Events): ce que la CLI et l'interface affichent pendant une installation
GET /api/v1/catalog?search=Le catalogue, avec les apps installéesdotbox list
GET /api/v1/apps/{app}Ce que l'on sait d'une app: image, état, adresse, accès, dossiers, portsdotbox info
POST /api/v1/apps/{app}/start, /stop, /restartDémarre, arrête ou redémarre une app. Rend une tâchedotbox start, stop, restart
GET /api/v1/apps/{app}/logs?tail=&follow=Les logs d'une app ou d'un container du core, en fluxdotbox logs
POST /api/v1/updateRelit le catalogue sur GitHub, puis met à jour les apps demandées, {"apps": [...], "all": true, "rollback": false}. Rend une tâchedotbox update
GET /api/v1/diffLe plan: l'écart entre ce qui est voulu et ce qui tourne, une ligne par écart. Chacune dit ce que dotbox sync en fera (sync, vide s'il la laisse, une version par exemple) et si c'est une app arrêtée avec dotbox stop (info), qui n'est pas un écartdotbox diff
POST /api/v1/syncApplique le plan, {"plan": [...]}: celui que la CLI a montré, tel que GET /api/v1/diff l'a rendu. Le service le recalcule et répond 409 s'il a changé entre-temps, ou s'il n'y a rien à faire. Rend une tâchedotbox sync
POST /api/v1/backupLance une sauvegarde, {"app": "radarr", "to": "/srv/backups"} (les deux facultatifs). Rend une tâche. Son résultat: les archives, leur taille, les destinations. restore n'a pas de route: il se fait en root, sans le servicedotbox backup
GET /api/v1/configLes clés de dotbox.yml que dotbox config connaît, avec leur valeur, [{"key": "domain", "value": "example.com"}, ...]dotbox config get
GET /api/v1/config/{key}Une seule clé, au même format. Une clé inconnue, pas encore prise en charge ou d'une app qui n'est pas installée reçoit 400, avec le motifdotbox config get <key>
PUT /api/v1/config/{key}Vérifie la valeur, {"value": "example.org"}, puis écrit dotbox.yml, sans rien appliquer. Rend l'ancienne et la nouvelle valeur, changed (faux quand c'était déjà la valeur: rien n'est écrit) et un avertissement s'il y en a un (les passkeys, pour le domaine). Une valeur refusée reçoit 400, avec le motif. Pas une tâche: un fichier écritdotbox config set

Une tâche à la fois: une seconde demande pendant une installation reçoit 409, avec la tâche en cours. dotbox upgrade et dotbox completion n'ont pas de route: la première remplace le binaire du service, la seconde ne regarde que la CLI. Les autres commandes de la page CLI viendront avec leur route.

Un exemple

La CLI ne fait rien d'autre que cette requête, puis met la réponse en forme:

$ curl -s --unix-socket /run/dotbox/dotbox.sock http://dotbox/api/v1/status
{
  "core": [
    { "name": "traefik", "version": "v3.7.19", "state": "running", "health": "healthy",
      "setup_pending": false }
  ],
  "apps": [
    { "name": "radarr", "version": "7.0.3.10918-ls328", "state": "running", "health": "healthy",
      "url": "https://radarr.example.com", "access": "two_factor", "setup_pending": false }
  ],
  "doctor": { "date": "2026-11-20T14:02:00Z", "problems": 2 }
}

Si le service ne répond plus

La CLI le dit, avec la commande pour le relancer (sudo systemctl restart dotbox). En SSH, sudo dotbox --local fait le même travail sans le service, directement depuis la commande.

What it is

The dotbox binary serves twice. Run as a service, dotbox serve, it does the work: it drives Docker, writes the files in /opt and checks the server. Run as a command, dotbox status, it asks the service for that work and prints the answer. The web interface does the same, through the same routes.

  • The service runs as root, under systemd (dotbox.service), installed and started by dotbox init with the core.
  • One binary for both: the CLI and the service always have the same version.
  • All the logic is in the service. The CLI needs no special rights, so no sudo.

Two doors, none on the Internet

DoorWho uses itWho is allowed
/run/dotbox/dotbox.sock, a Unix socketThe CLI, on the serverRoot, and members of the dotbox group. The service checks who is calling through the kernel, with no password or token.
https://dotbox.example.com, through TraefikThe web interfaceAn Authelia account in the admins group, with two_factor.

dotbox init adds your user to the dotbox group. It is not the docker group: it only grants Dot Box's actions, on catalog apps. Running an arbitrary container, mounting a server folder or reading a secret stays root only.

What protects it

  • The service never listens on a public address. On the web side, it listens on the server's address in the dotbox network, which only Traefik should reach.
  • Traefik adds a secret header to each request, drawn by dotbox init and kept in /opt/dotbox/secrets/. The service refuses any web request without it: an app on the dotbox network cannot call it by posing as Traefik.
  • The service only trusts the name sent by Authelia (Remote-User, Remote-Groups) along with that header.
  • Actions only root can do go through sudo, without the service: dotbox init, dotbox upgrade, dotbox restore, dotbox authelia, dotbox exec, dotbox edit, dotbox add and --local. These are the ones that would give root to whoever runs them: a command in a container, a compose or an archive that can mount any folder of the server.

Routes

JSON over HTTP, under /api/v1. A change that breaks clients will go through /api/v2.

RouteWhat it doesCommand
GET /api/v1/versionThe service's version and its binary's checksum: dotbox init restarts it when the binary has changed
GET /api/v1/statusThe core and the apps: version, state, address, access, the last doctor's summary, and the last full backup with the next one (backup)dotbox status
GET /api/v1/doctorThe last doctor's result
POST /api/v1/doctorRuns the checks and returns their resultdotbox doctor
GET /api/v1/motdThe lines of the SSH welcome message, as at login: the fast ones read now, the slow ones from their cache, each with its agedotbox motd
POST /api/v1/motd/refreshRuns the cached checks again (doctor, the catalog, the latest release, Debian updates, CrowdSec), then returns the message. A check that fails keeps its last value and its agedotbox motd --refresh
POST /api/v1/appsInstalls apps, {"apps": ["radarr", "sonarr"]}. Returns a job, which can be followed livedotbox install
DELETE /api/v1/apps/{app}Removes an app (?purge=true to delete everything). Returns a jobdotbox remove
GET /api/v1/jobs/{id}/eventsA job's steps, live (Server-Sent Events): what the CLI and the interface show during an install
GET /api/v1/catalog?search=The catalog, with the installed appsdotbox list
GET /api/v1/apps/{app}What is known about an app: image, state, address, access, folders, portsdotbox info
POST /api/v1/apps/{app}/start, /stop, /restartStarts, stops or restarts an app. Returns a jobdotbox start, stop, restart
GET /api/v1/apps/{app}/logs?tail=&follow=The logs of an app or a core container, streameddotbox logs
POST /api/v1/updateReads the catalog on GitHub again, then updates the apps asked for, {"apps": [...], "all": true, "rollback": false}. Returns a jobdotbox update
GET /api/v1/diffThe plan: the gap between what is wanted and what runs, one line per gap. Each says what dotbox sync will do with it (sync, empty if it leaves it, a version for example) and whether it is an app stopped with dotbox stop (info), which is not a gapdotbox diff
POST /api/v1/syncApplies the plan, {"plan": [...]}: the one the CLI showed, as GET /api/v1/diff returned it. The service computes it again and answers 409 if it changed in between, or if there is nothing to do. Returns a jobdotbox sync
POST /api/v1/backupRuns a backup, {"app": "radarr", "to": "/srv/backups"} (both optional). Returns a job. Its result: the archives, their size, the destinations. restore has no route: it runs as root, without the servicedotbox backup
GET /api/v1/configThe keys of dotbox.yml that dotbox config knows, with their value, [{"key": "domain", "value": "example.com"}, ...]dotbox config get
GET /api/v1/config/{key}A single key, in the same format. An unknown key, one not handled yet or one of an app that is not installed gets 400, with the reasondotbox config get <key>
PUT /api/v1/config/{key}Checks the value, {"value": "example.org"}, then writes dotbox.yml, applying nothing. Returns the old and the new value, changed (false when it already was the value: nothing is written) and a warning if there is one (passkeys, for the domain). A refused value gets 400, with the reason. Not a job: a file writtendotbox config set

One job at a time: a second request during an install gets 409, with the running job. dotbox upgrade and dotbox completion have no route: the first replaces the service's binary, the second only concerns the CLI. The other commands of the CLI page will come with their route.
