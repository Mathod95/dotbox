Les trois utilisent le même format de manifest: une app du Sandbox ou une des tiennes suit les mêmes chemins, le même réseau et les mêmes règles d'accès que le reste, et elle est sauvegardée de la même façon.

Ajouter ta propre app

$ sudo dotbox add ./compose.yml --name it-tools
$ dotbox install it-tools

add lit le fichier compose du projet et en fait un manifest, dans /opt/dotbox/apps/it-tools.yml. Il reprend du compose l'image, le port web (le premier exposé, ou --port), les dossiers et l'environnement, et ajoute ce que Dot Box met à chaque app: sous-domaine, accès two_factor, réseau dotbox, PUID et PGID, dossiers rangés dans /opt/it-tools et /data. L'image doit avoir une version fixée, jamais latest. Relis le manifest avant d'installer: dotbox install cherche d'abord dans tes apps, puis dans le catalogue.

Un seul container pour l'instant: le moteur ne sait pas encore installer une app à plusieurs containers (une base de données à côté, par exemple). Un compose à plusieurs services, comme celui d'Immich, est refusé, avec ce motif. add passe par sudo: un compose peut monter n'importe quel dossier du serveur.

Proposer une app au Sandbox

Une app qui marche chez toi peut rejoindre le Sandbox par une pull request sur Mathod95/dotbox-sandbox. Son manifest doit:

  • utiliser une image publique avec une version fixe, jamais latest;
  • ranger sa config dans /opt/<app> et ses données sous /data;
  • déclarer son niveau d'accès (two_factor, one_factor, app ou public);
  • avoir un pictogramme 7 × 7 pour le catalogue.

Apps retirées

Une app peut quitter le Sandbox, par exemple quand le projet est abandonné. Elle continue de tourner chez toi: son compose.yml reste dans /opt/<app>. dotbox status la marque « hors catalogue », et dotbox remove la retire quand tu veux.

Add your own app

$ sudo dotbox add ./compose.yml --name it-tools
$ dotbox install it-tools

add reads the project's compose file and turns it into a manifest, in /opt/dotbox/apps/it-tools.yml. It takes the image, the web port (the first one exposed, or --port), the folders and the environment from the compose, and adds what Dot Box gives every app: subdomain, two_factor access, dotbox network, PUID and PGID, folders placed in /opt/it-tools and /data. The image must have a pinned version, never latest. Review the manifest before installing: dotbox install looks in your apps first, then in the catalog.

One container for now: the engine cannot install an app with several containers yet (a database alongside, for example). A compose with several services, like Immich's, is refused, with that reason. add goes through sudo: a compose can mount any folder of the server.

Submit an app to the Sandbox

An app that works for you can join the Sandbox through a pull request on Mathod95/dotbox-sandbox. Its manifest must:

  • use a public image with a pinned version, never latest;
  • keep its config in /opt/<app> and its data under /data;
  • declare its access level (two_factor, one_factor, app or public);
  • have a 7 × 7 pictogram for the catalog.

Retired apps

An app can leave the Sandbox, for example when its project is abandoned. It keeps running on your server: its compose.yml stays in /opt/<app>. dotbox status marks it "off catalog", and dotbox remove removes it whenever you want.
