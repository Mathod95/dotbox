Updates●Dot Box and your apps, separately, and only when you decide.

Qui met à jour quoi

QuoiComment
Le binaire dotboxsudo dotbox upgrade, plus bas.
Les appsdotbox update, plus bas.
Le core (Traefik, Authelia, CrowdSec)sudo dotbox init relit le catalogue sur GitHub et ne recrée que ce dont la version a changé.

Une app qui demande une version plus récente de Dot Box refuse de s'installer ou de se mettre à jour, et le dit: mets d'abord le binaire à jour.

Mettre à jour Dot Box

$ sudo dotbox upgrade

Remplace le binaire par la dernière release de GitHub, après avoir vérifié son SHA-256, garde l'ancien dans /usr/local/bin/dotbox.previous et redémarre le service. Ne touche ni aux apps ni au core. Pour revenir à l'ancien binaire: sudo install -m 755 /usr/local/bin/dotbox.previous /usr/local/bin/dotbox. Plus tard, si une nouvelle version change le format des manifests ou de dotbox.yml, upgrade convertira les fichiers et l'indiquera dans son résumé.

Mettre à jour une app

$ dotbox update radarr
$ dotbox update --all

Sans sudo: la commande passe par le service. Chaque manifest fixe une version d'image (lscr.io/linuxserver/radarr:7.0.3.10918-ls328), jamais latest: ce qui tourne est toujours connu. update relit d'abord le catalogue sur GitHub, passe chaque app à la version du catalogue, recrée son container et attend qu'il soit Running avant de passer à l'app suivante. Une app qui ne repart pas arrête la série. Une app arrêtée avec dotbox stop reçoit sa nouvelle version et reste arrêtée. Le core ne passe pas par update: sudo dotbox init le met aux versions du catalogue.

Les nouvelles versions viennent du catalogue, le dossier catalog/ du repo Mathod95/dotbox: Renovate y propose chaque nouvelle version et la CI la teste. Un correctif fusionne seul sur main quand la CI passe, une version plus grande attend d'être relue. Dot Box relit le catalogue à chaque dotbox update et à chaque sudo dotbox init, sans changer de binaire. dotbox diff et dotbox sync s'en tiennent au catalogue déjà rangé sur le serveur, sans aller sur GitHub.

Revenir en arrière

$ dotbox update radarr --rollback

Avant chaque mise à jour, update note l'image qui tournait dans /opt/<app>/.dotbox-previous: --rollback la remet en place si la nouvelle version pose problème. Une seule marche en arrière: la note est effacée après usage. Une app arrêtée avec dotbox stop reste arrêtée.

Voir ce qui est disponible

$ dotbox update
  ✓ [1/1] Catalog       90161a8 of 2026-11-19          2.4 s

◇  prowlarr   3.0.2.5780-ls169      up to date
▲  radarr     7.0.3.10918-ls328     → 7.0.4.10950-ls329
▲  sonarr     4.0.20.3014-ls329     → 4.0.21.3030-ls330

  2 apps to update: dotbox update --all, or dotbox update <app>

dotbox update sans app relit le catalogue et dit seulement ce qui est en retard, sans rien changer. dotbox diff montre aussi une version en retard (« runs …, the catalog has … »), mais par rapport au catalogue déjà rangé sur le serveur.

Mises à jour automatiques

À venir. Désactivées par défaut: une mise à jour se fait quand tu la lances. Pour les programmer, une section dans dotbox.yml, sans Watchtower:

update:
  schedule: sunday 05:00
  apps: [radarr, sonarr, prowlarr]   # ou all

Une sauvegarde de chaque app concernée est faite juste avant.

WhatHow

An app that needs a newer Dot Box refuses to install or update, and says so: update the binary first.

Update Dot Box

$ sudo dotbox upgrade

Replaces the binary with the latest GitHub release, after checking its SHA-256, keeps the old one in /usr/local/bin/dotbox.previous and restarts the service. Touches neither the apps nor the core. To go back to the old binary: sudo install -m 755 /usr/local/bin/dotbox.previous /usr/local/bin/dotbox. Later, if a new version changes the manifest or dotbox.yml format, upgrade will convert the files and say so in its summary.

Update an app

$ dotbox update radarr
$ dotbox update --all

No sudo: the command goes through the service. Each manifest pins an image version (lscr.io/linuxserver/radarr:7.0.3.10918-ls328), never latest, so what runs is always known. update first reads the catalog on GitHub again, moves each app to the catalog's version, recreates its container and waits for it to be Running before moving to the next app. An app that fails to restart stops the run. An app stopped with dotbox stop gets its new version and stays stopped. The core does not go through update: sudo dotbox init brings it to the catalog versions.

New versions come from the catalog, the catalog/ folder of the Mathod95/dotbox repository: Renovate proposes each new version there and CI tests it. A patch merges into main on its own when CI passes, a bigger version waits for a review. Dot Box reads the catalog again on every dotbox update and every sudo dotbox init, without changing its binary. dotbox diff and dotbox sync stick to the catalog already stored on the server, without going to GitHub.

Roll back

$ dotbox update radarr --rollback

Before each update, update writes down the image that was running in /opt/<app>/.dotbox-previous: --rollback puts it back if the new version causes trouble. One step back only: the note is deleted once used. An app stopped with dotbox stop stays stopped.
